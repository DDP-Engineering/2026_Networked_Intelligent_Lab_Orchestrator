## Frame

Problem: a clean appliance answers on no interface. The management allowlist is
always an administrator's explicit choice, `serve` refuses to start without one,
and nothing reads the commissioning state recorded by the previous work package.
An installer with a new Mini PC therefore has no way in.

Desired outcome: while the appliance has not completed commissioning it serves
management access on every eligible physical interface, follows the hardware as
adapters appear and disappear, resumes the same allowlist after a restart, and
stops deriving the moment it is commissioned.

Actors: Bench Core startup and its reconcile loop (derive and apply); the
privileged helper firewall and the socket gate (enforce); the installer (reaches
the appliance); an administrator on a commissioned appliance (the only source of
allowlist change from then on).

Primary scenario: a provisioning appliance starts with no listener option -> it
derives the allowlist from every eligible physical interface, persists it, and
applies it to the helper firewall and the socket gate before serving -> an
adapter connected later joins on the next reconcile, and one removed leaves.

Examples: a Mini PC with built-in Ethernet, Wi-Fi and a USB Ethernet adapter is
reachable on all three; a USB adapter connected five minutes into provisioning
begins carrying management access without a restart.

Counterexamples: a container veth or bridge never joins, because it is not
eligible; a USB adapter connected after commissioning never joins; an explicit
management-access update is refused while provisioning, because the allowlist is
derived there and the only way to change it is to commission.

In scope: a provisioning mode on `ManagementAccessService` that derives,
persists, applies and re-derives the allowlist; the freeze after commissioning;
`serve` accepting no listener option while provisioning and refusing it when
commissioned; focused Go tests over a controlled provider and a recording
firewall.

Out of scope: link-local addressing, mDNS, the certificate identities beyond the
one name a derived configuration needs to validate, the transition that
completes commissioning, and every GUI and HTTP payload change. Nothing here
completes commissioning; the state only ever reads `provisioning` in this task.

Constraints: the existing three-layer enforcement is preserved exactly -
helper nftables table, socket `Accept` gate and the per-request recheck - and no
new privilege reaches the unprivileged process. `ManagementAccessConfiguration`
requires at least one interface and one TLS name, so a derived configuration that
has no eligible interface cannot be persisted or applied; that case must fail
closed rather than relax the validation. `serve` computes its listener address
before `app.New` opens the database, so the commissioning state cannot be read
until after the open.

Success signals: a derived allowlist reaches both the firewall and the socket
gate; an adapter appearing mid-provisioning is admitted and one appearing after
commissioning is not; a restart resumes the same allowlist; `serve` starts with
no listener option only while provisioning.

Proposed behaviors:
1. While not commissioned, the allowlist is every eligible physical interface,
   recomputed on reconcile and persisted.
2. Once commissioned, the allowlist is the configured set alone and a new

3. `serve` starts with no listener option while provisioning, and refuses with a
   message naming the options it needs when the appliance is commissioned.

Path and reason: full. New externally observable behavior, a new option on an
existing service contract, no existing requirement covers it, and it changes
where management access is exposed.

## Design

**Requirements coverage.** REQ-FUNC-243c38a6 and REQ-SEC-a1012bc5 are both
carried by a provisioning mode inside `ManagementAccessService`;
REQ-PLAT-b1abf074 by the `serve` option handling in `cmd/nilo/main.go`.

**Component responsibilities.** *Bench Core foundation* throughout. The service
keeps sole ownership of the allowlist, the helper firewall call and the socket
gate: a second writer to the `inet nilo_management` table is exactly the
split-brain the ticket's one-backend constraint forbids. The `serve` command
owns only which mode it asks for and refusing a combination the appliance state
does not permit.

**Interfaces and contracts.**

- `ManagementAccessOptions` gains `Provisioning bool` and
  `ProvisioningTLSNames []string`. `Provisioning` means "derive the allowlist";
  it is set by `serve` from `App.Commissioning()`.
- `deriveProvisioningInterfaces([]Interface) []string` - the eligible interface
  names, sorted, reusing `EligibleForManagement`.
- `ManagementAccessService.Update` and `Confirm` return a new
  `ErrManagementAccessDerived` while provisioning: the allowlist is not an
  administrator's to set there.

**Execution flow.** In provisioning mode `NewManagementAccessService` derives
from the observed interfaces instead of requiring `Initial` or a saved record,
and `refresh` re-derives on every reconcile. When the derived set differs from
the record, the service applies the helper firewall, persists, and rebuilds the
socket allowlist through the path `refresh` already uses, so a derived change
gets the same ordering and the same failure handling as an administrator's.

**Failure recovery.** A provisioning appliance with no eligible interface
present cannot build a configuration that passes `Validate`, which requires at
least one interface. It therefore persists nothing, applies no firewall rule and
admits nothing until an eligible adapter appears, at which point the ordinary
reconcile path applies it. Failing closed is the only safe reading: relaxing
`Validate` to accept an empty allowlist would turn the wildcard listener into an
unguarded one, and an empty nftables interface set is not expressible anyway.

**Security and trust boundaries.** Unchanged: the helper still receives a
validated port and interface list and nothing else, the socket gate still
rejects a disallowed destination before TLS, and the per-request recheck still
runs outside the application handler. The widening is bounded by the durable
lifecycle state rather than by a process flag, which is what makes the freeze
survive a restart.

**Compatibility and migration.** An appliance that passes `--bind` or the
interface-managed options keeps exactly its current behavior; provisioning mode
is reachable only when no listener option is given. `serve` adopts the
first-boot wildcard before `app.New` because `config.Load` only records
`BindAddress`, then refuses after the open when the appliance turns out to be
commissioned - so the refusal names the real reason rather than a syntax rule.

**Test seams.** `internal/network/management_provisioning_test.go` over a
provider whose interface list the test controls, a recording firewall and an
in-memory store: derivation, admission and refusal by destination address,
mid-provisioning appear and disappear, restart resumption, the commissioned
freeze, and the refusal of `Update` while provisioning.
`cmd/nilo/main_test.go` for the two `serve` outcomes.

**Alternatives rejected.** A separate provisioning service beside the
management one - two writers to one firewall table and one record. A runtime
`--first-boot` flag instead of the durable state - it would not survive a
restart and could be passed to a commissioned appliance. Relaxing `Validate` to
allow an empty allowlist - it would make an unguarded wildcard listener one
mistake away.

**Expected files.** `internal/network/management_access.go`,
`internal/network/management_provisioning_test.go` (new), `cmd/nilo/main.go`,
`cmd/nilo/main_test.go`.

**Architecture.** Behavior-only; no component boundary moves.

**Risks.** Derivation runs on the reconcile cadence, so an adapter appears
within one sampling interval rather than instantly; the ticket asks for it to
begin serving when it appears, not within a stated latency.

**Open decisions.** None.
