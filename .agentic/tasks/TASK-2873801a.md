## Frame

Problem: NILO cannot tell a physical management-capable adapter from a virtual
system interface. The privileged helper maps NetworkManager device types 1
(ethernet) and 20 (veth) onto the same `network.KindEthernet`, and
`network.Interface` carries no physical/virtual signal, so a container veth pair
or a transient bridge is indistinguishable from built-in Ethernet. Every later
first-boot provisioning behavior decides exposure from this classification, so
without it the appliance would offer management access inside a container
network.

Desired outcome: one name-independent classification, derived from hardware
facts, that names the set of physical Ethernet and Wi-Fi adapters eligible to
carry NILO management access, and excludes loopback, WireGuard, veth, bridges,
tun/tap and other non-management system interfaces.

Actors: the privileged network helper (observes NetworkManager and the kernel);
Bench Core (consumes the classification); later first-boot provisioning,
commissioning and GUI behaviors (the only callers that act on it).

Primary scenario: the helper reads a device -> it records whether that device is
a real physical adapter alongside the existing kind, name and adapter identity ->
Bench Core answers "is this interface eligible for management provisioning?" from
those recorded facts alone, never from the interface name.

Examples: built-in `enp1s0` with a permanent hardware address and a real bus
device is eligible; a USB Ethernet adapter appearing as `enx00e04c680001` is
eligible on the same evidence, with no name rule involved; `wlp2s0` is eligible.

Counterexamples: `veth7a3b1c` inside a container network presents
NetworkManager device type 20 and is reported as `KindEthernet` today - it is not
eligible; `docker0` and a transient bridge are not eligible; `lo` and a WireGuard
tunnel device are already excluded by kind and stay excluded.

In scope: a physical-adapter signal on `network.Interface`; its population in the
live NetworkManager helper; one portable eligibility predicate in the `network`
package; simulated-catalog entries that make the exclusions provable without
hardware; focused Go tests for all three.

Out of scope: using the classification to change any exposure, allowlist,
firewall rule or listener - that is a later work package; commissioning
lifecycle state; mDNS; link-local addressing; any HTTP API field; any GUI
change. The administrator API payload `networkInterfacePayload` is deliberately
left unchanged in this task.

Constraints: the classification logic must be testable on the Windows
development host, so the D-Bus and sysfs reads stay in the existing
`//go:build linux` files and only their results feed a portable predicate -
the separation `nftables_render.go` / `nftables_linux.go` already uses
(OBSERVED: `05_Software/nilo_assistant/internal/nethelper/nftables_render.go`,
`nftables_linux.go`). No interface-name matching anywhere in the rule. The
unprivileged process gains no new capability: this task only reads.

Success signals: a test proves a veth-shaped and a bridge-shaped interface are
classified ineligible while ethernet and Wi-Fi adapters are eligible; a test
proves the rule never consults the interface name; the simulated catalog carries
an ineligible virtual interface so every later exposure test can assert against
it; `go build ./...` and the focused package tests stay green.

## Design

**Requirements coverage.** REQ-FUNC-7ae21313 is carried by a new portable
predicate in the `network` package plus two simulated-catalog entries.
REQ-PLAT-18084875 is carried by a new portable decision function and bus-device
probe in `nethelper`, called from the existing Linux device reader.

**Component responsibilities.** Both requirements land in *Bench Core
foundation*. The privileged helper keeps sole ownership of observing the host:
it decides whether a device is a physical adapter and records that on the
reading it already returns. The `network` package owns the product rule and
never observes anything itself, so the same rule holds for the simulated
provider, the live helper and any future provider. Nothing in this task reads
the classification: management access, device networks, the HTTP API and the GUI
are untouched.

**Interfaces and contracts.**

- `network.Interface` gains `Physical bool` - whether the observing provider saw
  a physical network adapter. The zero value is `false`, so a reading from a
  provider that does not populate it, or a hand-built literal in an existing
  test, is never treated as an eligible management path. Fail-closed is the
  deliberate choice here (REQ-FUNC-7ae21313).
- `network.EligibleForManagement(Interface) bool` - the one rule: kind is
  `KindEthernet` or `KindWiFi`, the reading is `Physical`, and its adapter
  identity is non-empty after the package's existing `canonicalAdapterID`
  normalization. No other input, and no interface name (REQ-FUNC-7ae21313).
- `nethelper.physicalAdapter(permanentHardwareAddress string, busDevice bool) bool` -
  unexported, both signals required (REQ-PLAT-18084875).
- `nethelper.busDevicePresent(name string) bool` - stats
  `<busDeviceRoot>/<name>/device` and reports whether it resolves to a
  directory. `busDeviceRoot` is a package variable defaulting to
  `/sys/class/net` purely so a test can point it at a temporary tree.

**Deliberate placement.** The probe uses only `os.Stat` and `filepath.Join`, so
it compiles and tests on any host even though the path is meaningful only on
Linux. Keeping it out of a `//go:build linux` file is what makes
REQ-PLAT-18084875 verifiable on the Windows development host; only the D-Bus
read in `networkmanager_linux.go` stays tagged. This mirrors the existing
`nftables_render.go` / `nftables_linux.go` split.

**Execution flow.** `NetworkManager.device` already reads the `.Wired` or
`.Wireless` property set to obtain `PermHwAddress`. That value is captured into
a local and combined with `busDevicePresent(name)` through `physicalAdapter`,
and the result assigned to `d.Interface.Physical` before the reading is
returned. No new D-Bus call and no new round trip.

**Security and trust boundaries.** This task only reads. The unprivileged
process gains no capability, and the helper gains no new operation: the
classification travels on a reading the helper already returns. `busDevicePresent`
rejects an empty name and any name containing a path separator or NUL before
joining it to the root, so a hostile interface name cannot walk out of
`/sys/class/net` - defence in depth behind the validation `device` already
performs.

**Simulated catalog.** Two ineligible entries join the fixed catalog, both
connected so that a later exposure test cannot pass merely because they are
down:

- `veth9f2a41`, `KindEthernet`, `Physical: false`, adapter identity present,
  no address - the NetworkManager device-type-20 case that is reported as
  Ethernet today. Its adapter identity is deliberately non-empty, so the test
  proves `Physical` is what excludes it.
- `br-lab0`, `KindOther`, `Physical: false`, addressed `172.18.0.1/16` - an
  addressed, connected, ineligible interface.

Both are `Controllable: false` with a reason, preserving the existing catalog
invariant that an uncontrollable device always says why
(`provider_simulated_test.go::TestSimulatedCatalogMarksLoopbackNotControllableWithAReason`).
`enp1s0` and `wlan0` gain `Physical: true`, otherwise the simulation profile
would hold no eligible adapter at all.

**Compatibility.** `networkInterfacePayload` in `internal/httpapi/network.go`
is an explicit struct, so the new domain field does not reach `/api/v1` and no
client contract changes. The GUI keeps its own fixture in
`nilo_gui/src/api/mock.ts` and is not touched. The two new catalog entries are
observable under the simulation profile; no existing test asserts an exact
interface count against that catalog.

**Test seams.**

- `internal/network/eligibility_test.go` - table-driven over physical ethernet,
  physical Wi-Fi, virtual ethernet, bridge, loopback, WireGuard, and a physical
  adapter with an empty adapter identity, plus the swapped-name pair
  (`docker0` physical, `enp1s0` virtual) that settles name-independence.
- `internal/network/provider_simulated_test.go` - the catalog holds at least one
  eligible adapter and at least one non-loopback ineligible interface.
- `internal/nethelper/adapter_identity_test.go` - all four signal combinations,
  and the probe against a temporary tree with a device entry, without one, and
  for a name that is not a directory.

**Alternatives rejected.** Matching interface-name prefixes (`veth`, `br-`,
`docker`) - the requirement forbids it and a renamed adapter defeats it.
Trusting NetworkManager `DeviceType` alone - type 1 and type 20 are already
known to collide (`networkmanager_linux.go:102`). Deriving physicality inside
`network` from `AdapterID` alone - a veth has a stable `HwAddress` and would
pass. Adding an `EligibleInterfaces([]Interface)` filter now - no caller exists
until the provisioning allowlist work package, so it would ship untested and
unused.

**Expected files.** `internal/network/eligibility.go` (new),
`internal/network/eligibility_test.go` (new), `internal/network/model.go`,
`internal/network/provider_simulated.go`,
`internal/network/provider_simulated_test.go`,
`internal/nethelper/adapter_identity.go` (new),
`internal/nethelper/adapter_identity_test.go` (new),
`internal/nethelper/networkmanager_linux.go`.

**Architecture.** Behavior-only: no component boundary moves and no new
component appears, so no architecture drawing is owed. The *Bench Core
foundation* page is a legacy page without a `## Routing` change map; reconciling
it with the built code belongs to validate.

**Risks.** The `PermHwAddress` availability assumption is unresolved for
untested USB chipsets and is bounded by requiring both signals. `d.Interface.Physical`
cannot be exercised by an automated test on this host because the D-Bus read is
Linux-tagged; the decision it feeds is fully covered, and the assignment itself
is settled by the existing Linux system tests and the hardware acceptance run.

**Open decisions.** None.
