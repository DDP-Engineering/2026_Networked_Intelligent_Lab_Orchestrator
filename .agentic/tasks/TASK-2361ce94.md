## Frame

Problem: A user who does not know a NILO's address cannot reliably find or distinguish it. Current discovery depends on a shared provisioning name, a system hostname or UUID that is not printed, client-side DNS-SD support, an Ethernet path and prior knowledge of a server URL. Per-image TLS material also conflicts with distinct permanent appliance names.
Desired outcome: Every appliance has one printed permanent serial name and can be found, opened and physically identified from common clients and realistic lab topologies through independent standard discovery channels without weakening management-interface enforcement or exposing secrets.
Actors: Workshop installer, administrator, operator, viewer, nearby phone user, Windows/macOS/Linux client, router/DHCP-DNS service, Bench Core, privileged network helper and Raspberry Pi hardware.
Primary scenario: First boot derives and persists `nilo-<short-id>` -> helper personalizes TLS and publishes the name -> a user reads the label or discovers the appliance through mDNS, SSDP, DHCP DNS, Wi-Fi or the CLI -> opens the authenticated interface -> optionally sets a collision-checked friendly alias or triggers Identify.
Examples: Two fresh appliances on one switch answer distinct serial names simultaneously; a phone with no Ethernet joins an SSID named for the appliance and reaches the captive portal; Windows Network shows the appliance and removes it after management access is withdrawn; `nilo discover --json` merges mDNS and SSDP observations by UUID.
Counterexamples: Replacing the permanent serial name during a commissioning reset; publishing on a PLC, device-network, WireGuard or non-allowlisted interface; modifying a foreign NetworkManager profile; taking down the serial-name publication because `nilo.local` or a friendly alias collided; exporting a TLS private key from the helper; treating cross-VLAN multicast discovery as guaranteed.
In scope: Issue #17 packages 1-8: permanent identity and printable QR label; serial and friendly mDNS/DNS-SD names; helper-kept per-appliance TLS key and certificate lifecycle; interface-scoped SSDP presence and description; DHCP hostname/vendor identity on NILO-owned client profiles; provisioning-only Wi-Fi AP/DHCP/DNS/captive portal; GUI/button Identify; cross-platform CLI discover/open and discovered server names; appliance-local and authenticated About status; operations, first-boot and delivery documentation; automated and hardware acceptance evidence.
Out of scope: Cloud or central finder; cross-VLAN mDNS gateway or unicast DNS-SD; proprietary discovery protocol; Bluetooth, Improv, USB gadget, BOOTP or PXE provisioning; a desktop discovery application; password recovery or factory reset; building, burning or distributing an appliance image beyond the first-boot identity hook and label output; changes to the existing firewall, socket gate or per-request management-interface recheck.

Preserve the first-boot credential and signer-warning contracts already on master. The TLS private key must remain in the root helper keystore. Presence and unauthenticated surfaces must be narrowly interface- or loopback-scoped, deterministic and secret-free. Keep foreign profiles and protected adapter roles untouched. ## Design

### Architecture and responsibility boundaries

The permanent public identity and every private-key operation belong to the
root helper; SQLite owns only user-selected friendly presentation state. Bench
Core coordinates desired state and authenticated APIs, while the helper owns
link-local sockets, NetworkManager, Avahi, GPIO and commissioning services.
Client discovery remains an unprivileged CLI concern. This split satisfies
REQ-DATA-605c381f, REQ-SEC-618f47b2 and the existing typed-helper boundary in
REQ-SEC-83deb5c6 without moving the management access gates.

```text
 hardware identity + root keystore
              |
     nilo-nethelper (typed protocol)
      | TLS signer / Avahi / SSDP / NM / AP services / GPIO
      |                 per-interface, per-purpose groups
      v
 Bench Core naming + discovery coordinators ---- SQLite friendly/audit state
      |                       |
      | authenticated HTTPS   +---- separate loopback-only status listener
      v
 GUI About / label       nilo discover/open -- raw mDNS + SSDP clients
```

`internal/nethelper/appliance_identity.go` derives the versioned serial once,
stores its source class and fallback seed in the protected helper store, and
returns only public fields through a closed `appliance.identity.read` response
(REQ-DATA-605c381f). The installer supplies an explicit allowlist of generic
image hostnames; the helper replaces only an exact allowlisted value and marks
the attempt complete, so a custom hostname is never inferred or overwritten
(REQ-PLAT-8e42c96b). Commissioning reset continues to reset SQLite lifecycle
state only; helper identity, keys and the separate friendly-name column survive
(REQ-DATA-2c5b4a4d, REQ-FUNC-fb666359).

### Discovery publications and interfaces

The current single `MDNSAdvertisement` becomes a desired list of closed
`MDNSPublication` records keyed by `(purpose, interface)`, where purpose is one
of serial-service, provisioning-recovery or friendly-alias. The helper derives
its own Avahi group keys, reconciles only groups it owns, and reports status per
record. A failure or collision therefore cannot reset unrelated serial groups
(REQ-FUNC-554b9bbd, REQ-FUNC-6334add6, REQ-SEC-83deb5c6). The serial-service
record is present in provisioning and commissioned states, uses the serial as
SRV target and emits the specified v2 TXT data. `nilo.local` is a distinct
provisioning-only record. Friendly groups are per interface so one link's
collision rolls back the candidate without disturbing the permanent name.

SSDP follows the same desired-state boundary: Bench Core supplies validated
public metadata and current management addresses; the helper owns one multicast
socket/state machine per effective management interface and sends alive,
search-response and byebye messages. The existing effective-management set is
the only publication input, preserving the listener accept gate, request-time
recheck and firewall authority in REQ-SEC-a1012bc5. A minimal read-only device
description contains no control/event URLs and carries an HTTPS presentation
URL (REQ-FUNC-5a886873, REQ-FUNC-c143a4e8). The first build slice includes a
Windows 11 Network-view probe. If self-signed HTTPS in `LOCATION` is rejected,
only the description moves to a high-port, interface-scoped HTTP listener; the
presentation URL remains HTTPS. WS-Discovery is excluded unless that measured
probe proves SSDP insufficient.

The NetworkManager writer adds hostname and closed vendor identity only to
NILO-owned automatic IPv4/IPv6 client profiles. Manual, foreign, AP,
WireGuard, device and PLC profiles do not enter that function
(REQ-FUNC-1080011a). The existing owned IPv4LL path remains unchanged and gives
the CLI and mDNS a direct-cable seam (REQ-FUNC-d2d75f06).

### TLS and friendly-name state machine

The helper generates one ECDSA P-256 key and immutable certificate generations.
Bench Core receives certificate DER plus a generation-bound `crypto.Signer`
proxy; no protocol request returns a key, path, reusable handle or arbitrary
signing primitive. Certificates start 24 hours before generation, expire after
ten years and renew at 180 days remaining or whenever the advertised name set
changes. The previous generation remains signable for five minutes. Bench Core
limits signing to 32 concurrent calls with a five-second helper deadline and
publishes certificate snapshots atomically, so saturation fails an individual
handshake rather than the listener (REQ-SEC-618f47b2, REQ-REL-8010bcad). Existing
invalid-material refusal and actionable missing-SAN/signer warnings remain in
place (REQ-PLAT-3c35bacd); documentation says the credential is published but
the installed private key is per appliance (REQ-SEC-d0d3d4c4).

`internal/appliance/naming.go` serializes friendly-name changes under one
coordinator and uses idempotent helper transaction IDs. It validates the closed
body and DNS label, stages and activates certificate coverage for old plus
candidate, publishes all candidate interface groups, persists the SQLite
desired value, finalizes, then withdraws the old groups and surplus SAN. Any
collision withdraws every candidate group and restores the old certificate.
A crash reconciles the helper's staged transaction against the SQLite desired
value before normal publication. Reads require `network.read`; PUT/DELETE and
software Identify use the established administrator-only `network.manage` plus
session CSRF checks (REQ-FUNC-74521b89, REQ-FUNC-60826fdb).

### Provisioning AP and local-only surface

The commissioning coordinator deterministically chooses one eligible unused
Wi-Fi radio and asks NetworkManager for a NILO-owned WPA2 profile named by the
serial. It never displaces a protected, saved or active client profile. The
helper rejects the AP when `192.168.247.0/24` overlaps an existing route, starts
a directly-executed `dnsmasq` child from a root-owned generated config, and
runs a minimal in-process AP-address HTTP redirector. DHCP, DNS and redirect
bind only to that AP interface; their lifecycle is coupled to the owned profile
and commissioning state. Commissioning tears all of them down, while the
existing atomic reset brings them back (REQ-FUNC-8d482c89,
REQ-SEC-f3d137bb). The published first-boot password is supplied through the
installed helper configuration and is never placed in metadata or logs.

The optional appliance display uses a second HTTP server and a dedicated mux
that is configured only with a literal loopback address. It exposes safe names,
management addresses and the shared label image, has no mutation or proxy route,
and refuses startup for wildcard/non-loopback binds. It is not mounted into the
authenticated management handler (REQ-SEC-a7971222, REQ-SEC-1b1ab2b2).

### Identify, label, GUI and CLI

The existing hardware event queue gains the closed `identify` action without
renaming its durable recovery records. Identify is lowest priority: recovery
and reset supersede it, and it never changes lifecycle or network state. One
coordinator owns fake-clock-testable cadence, expiry and indicator restoration;
button Identify additionally requests best-effort reannouncement of the current
mDNS and SSDP sets. Migration 015 also adds a small Identify operation/outbox
record: the action state and bounded pending audit are made durable separately,
so an audit retry cannot replay the physical action. Audits reuse the Activity
repository with a closed action, source and outcome vocabulary
(REQ-PLAT-c6a335b0, REQ-FUNC-bfa4d4e5, REQ-SEC-7b9d9d6b).

One Go label package validates serial, normalized/sorted management MACs and the
permanent HTTPS URL, builds a QR matrix through a pinned pure-Go dependency and
renders escaped 62 mm by 29 mm SVG. The CLI emits the complete SVG to stdout
only after unique selection; About and loopback status serve the same renderer
as an image, avoiding browser-side raw-SVG injection (REQ-FUNC-17f9c447,
