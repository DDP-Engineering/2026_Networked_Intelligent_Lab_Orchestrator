## Design

The reconciled access model, the full permission matrix, the credential
shapes, the migration, the HTTP route table and the command-line surface are
written once in `.agentic/specs/REQ-SEC-5d0cfe7e.md` rather than duplicated
here. This section records only the decisions and the test seams.

**Two decisions, not one (REQ-SEC-5d0cfe7e, REQ-SEC-62e54172).** Identity
authorization answers "may this actor request this action"; integration
operation policy answers "may this operation run now, or does it need an
approval". The second is untouched and stays owned by the integration app.
Neither the Administrator role nor a fully scoped token changes approval
resolution or the core-enforced safety limits. Rejected alternative: folding
approvals into the permission matrix, which would have made an administrator
role a safety bypass and contradicted the MVP PRD's operation policy model.

**Fixed matrix compiled into the binary (REQ-SEC-5d0cfe7e).** Eight
permissions covering only functionality that exists: status, inventory, user
administration and token administration. Rejected alternative: a stored,
editable permission table, which the prompt excludes and which no current
endpoint could exercise.

**Effective permissions are recomputed per request (REQ-SEC-74b46e3e,
REQ-FUNC-7d80be16).** `rolePermissions(owner.role) ∩ scopes(token)` for a
token, `rolePermissions(user.role)` for a session, always from the stored
role. That is what makes a role change take effect immediately with nothing
to invalidate, and it makes scopes strictly subtractive. An empty scope list
means unnarrowed, which is what keeps tokens created before this work usable.

**Two credential kinds behind one resolution step (REQ-FUNC-db6fb2fa,
REQ-SEC-01c18c7c).** `httpapi` resolves either a `nilo_session` cookie or an
`Authorization: Bearer` header into one `identity.Actor` placed in the request
context; every route then declares the permission it needs. A missing or
unusable credential is 401, a usable credential without the permission is 403.
Rejected alternative: reusing the existing bearer middleware for browser
sessions too, which would have given automation tokens cookie semantics and
browser sessions no expiry of their own.

**Cookie mode is chosen, not inferred (REQ-SEC-b5502ddb).** `serve` takes
`--session-cookies development-localhost|https`, defaulting to the development
value and refusing that value on a non-loopback bind. Rejected alternative:
deriving `Secure` from the bind address, which silently produces an insecure
cookie the day the server moves behind a proxy.

**CSRF is a stored second verifier (REQ-SEC-49fe784b).** Login issues a CSRF
token in the body and in a readable cookie; only its SHA-256 verifier is
stored, next to the session. Rejected alternative: pure double-submit cookie
comparison, which needs no storage but accepts any attacker-set cookie pair.

**Login throttling is in-process (REQ-SEC-d8026dbe).** Per-username counter
with an injected clock, five failures per fifteen minutes. It resets on
restart, which is documented rather than hidden; a durable lockout table is
deferred.

**Identity service owns the invariants (REQ-SEC-8e89944b, REQ-SEC-e14c8f51).**
Last-enabled-administrator protection, session invalidation on disable and on
password reset, and audit emission all live in `internal/identity`, so the CLI
and the HTTP layer cannot each implement them differently.

**Forward migration only (REQ-DATA-d8d5a701).**
`004_identity_access_control.sql` adds columns and the `user_sessions` table;
`001`-`003` are untouched, and the existing digest ledger would refuse a
rewrite anyway. Existing identities default to Viewer.

**Test seams.** `identity.Service` takes an injected clock and an injected
random source, so expiry, throttling windows and token generation are
deterministic (REQ-FUNC-db6fb2fa, REQ-SEC-d8026dbe, REQ-FUNC-ae14f9d3).
`httpapi.NewHandler` takes the identity service and the cookie mode, so every
authorization case is driven through the production handler with
`httptest` (REQ-SEC-62e54172, REQ-SEC-b5502ddb, REQ-SEC-49fe784b,
REQ-SEC-01c18c7c, REQ-TEST-add2dfbd). The SQLite repositories are exercised
against a real temporary database that is closed and reopened, which is how
the migration and the persistence claims are settled (REQ-DATA-d8d5a701).
`cmd/nilo` tests build and run the real binary with piped stdin, which is how
the bootstrap restriction, the password-never-in-argv rule and the one-time
token disclosure are settled (REQ-FUNC-00305f82, REQ-FUNC-519eff58,
REQ-FUNC-ae14f9d3, REQ-FUNC-e325f08e).

**Knowledge architecture.** `bench-core-foundation.md` gains the identity
service and the session store in its diagram and file list; no other component
page changes shape.
