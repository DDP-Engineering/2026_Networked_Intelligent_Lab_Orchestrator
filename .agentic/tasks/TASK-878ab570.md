## Frame

Problem: a first-boot appliance is reachable only by an address the installer
has to discover. The ticket asks for one URL that works from whichever network
the installer happens to be on, and NILO publishes no name at all.

Desired outcome: while being commissioned, the appliance answers its configured
local name on exactly the interfaces currently carrying management access,
publishing whatever addresses those interfaces hold, and renews that publication
as adapters come and go.

Actors: the privileged helper (owns the responder); Bench Core's reconcile loop
(keeps the publication in step); the installer (types one URL).

Primary scenario: provisioning derives its allowlist -> Bench Core asks the
helper to answer `<name>.local` on those interfaces -> the helper writes
responder configuration it owns and reloads it -> an adapter joining or leaving
renews the publication on the next reconcile.

Examples: `https://ddp-remote.local:8443` reaches the appliance over the
built-in Ethernet, over Wi-Fi, and over a USB adapter plugged in later.

Counterexamples: the responder never answers on loopback or on an interface
outside the allowlist; an appliance that already has responder configuration
somebody else wrote is left alone; a helper with no responder reports that it
cannot publish rather than appearing to succeed.

In scope: the advertisement type and its validation, the responder configuration
renderer and its ownership check, the privileged operation and its envelope
guard, the Linux driver, and the announcer that keeps the publication in step.

Out of scope: certificate identities and the missing-SAN warning, the browser
interface, and the appliance image's responder package. Nothing here reads or
writes a certificate.

Constraints: RULING-001 settles the mechanism - the helper drives avahi rather
than NILO answering mDNS in process. The unprivileged process must never send
configuration text, and NILO manages only configuration it wrote, the same
discipline the nftables tables already use.

Success signals: the rendered configuration names exactly the derived interfaces;
an advertisement is refused by every operation but publication; foreign
configuration is recognized and refused; the announcer republishes only on
change and retries after a failure.

Evidence:

  `absent`, `owned` and `foreign` is the established ownership discipline.
- OBSERVED `internal/nethelper/protocol.go` - `Request` is a closed envelope and
  each payload field is refused by every operation but its own.
- OBSERVED `internal/nethelper/management_nftables.go` - the owned-resource

  the Linux build tag.
- OBSERVED `cmd/nilo/main.go` - the reconcile wrapper that already re-derives the
  provisioning allowlist is where the publication is kept in step.
- STATED (user, issue #6) - "Advertise the configured appliance hostname through
  mDNS on every active provisioning interface" and "Make the same HTTPS URL
  usable from each directly connected or local network where name discovery is
  supported"; acceptance test 3.
- STATED (user, RULING-001 on TASK-2873801a) - the helper drives avahi.

Assumptions: the appliance image carries a responder the helper can drive. A
helper without one reports that it cannot publish, and the appliance stays
reachable by address.

Unknowns: none blocking.

Decision-blocking questions: none.

Proposed behaviors:
1. The appliance answers its local name on exactly the interfaces carrying
   management access, renewing the publication when that set changes, and
   reports rather than hides a publication it could not make.
2. The helper accepts a validated advertisement rather than configuration text,
   manages only configuration it wrote, and reports an appliance it cannot
   publish on.

Path and reason: full. A new privileged operation, a new protocol payload and a
new externally observable behavior.

## Design

**Requirements coverage.** REQ-FUNC-554b9bbd is carried by
`network.MDNSAdvertisement`, `network.MDNSAnnouncer` and the reconcile wiring;
REQ-SEC-83deb5c6 by the protocol envelope guard, the ownership check and the
engine's refusal path.

**Component responsibilities.** *Bench Core foundation*. The `network` package
owns what should be published and when; the helper owns how. The unprivileged
process sends a validated advertisement - one host label and a list of interface
names - and never responder syntax, which is the same contract the management
firewall already has.

**Interfaces and contracts.** `MDNSAdvertisement{HostName, Interfaces}` with
`Validate` refusing a name that is not a single DNS label, an empty interface
list, loopback, a duplicate, or anything that could carry a configuration
separator into the rendered file. `MDNSPublisher` is the narrow interface the
domain declares and the helper client satisfies. Helper operation
`mdns.publish`, refused by every other operation's envelope. `MDNSDriver` with
`MDNSConfigurationState` and `InstallMDNS`, satisfied by the Linux
`NetworkManager`.

**Failure recovery.** A publication that fails is reported, recorded as
unpublished, and retried on the next reconcile: an appliance whose name is not
answered is still reachable by address, so this must not be fatal, and it must
not be silent either. An advertisement with no usable interface publishes
nothing and reports no error, because that is an ordinary first-boot moment
rather than a fault.

**Security and trust boundaries.** The request type gains one field that holds a
host label and interface names, both validated before rendering. The helper
refuses configuration it did not write, so an appliance already running a
responder is never taken over. The rendered configuration publishes only the
name and addresses, explicitly disabling the responder's optional host
information.

**Compatibility.** Additive: an appliance in any other mode publishes nothing and
the helper gains one operation. Configuration is written to a staged file and
renamed over its target, so a reading responder never sees a half-written file.

**Alternatives rejected.** An in-process Go responder - RULING-001 settled this,
and it would contend with a running avahi for port 5353. Publishing a fixed
address rather than the interfaces' own - it would break on DHCP renewal, which
is the thing the ticket asks to survive.

**Expected files.** `internal/network/mdns.go`, `mdns_announcer.go`,
`mdns_announcer_test.go`, `internal/nethelper/avahi_render.go`,
`avahi_render_test.go`, `avahi_linux.go`, `mdns.go`, `client.go`, `protocol.go`,
`engine_test.go`, `cmd/nilo/main.go`.

**Open decisions.** None.
