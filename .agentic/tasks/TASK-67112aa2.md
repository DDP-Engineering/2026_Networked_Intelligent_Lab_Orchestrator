## Frame

Problem:
The repository gate proves NILO against a runtime it will not ship. Both gate
routes run the browser suite, and that suite builds and starts a
simulation-profile Bench Core. `.agentic/context/project.md` and
`.agentic/context/environment.md` describe appliance-only operation, so the
agreed direction and the tree disagree. The simulation profile cannot be
removed first: removing it before the verification story moves turns the gate
red in between.

Desired outcome:
A verification stage in which Bench Core runs in its shipping configuration -
`--profile appliance`, TLS material, a built interface directory and a real
privileged helper - against a real NetworkManager reporting adapters it
actually detected, inside a disposable network namespace that cannot reach the
developer's own connection. The stage exists and is proven before anything is
removed from Bench Core.

Actors:
A developer running the repository gate on a supported host; the automated gate
(`05_Software/scripts/aegis_test.py`, `02_Tools/env/with-build-environment.*`);
Bench Core as the unprivileged service account; `nilo-nethelper` as the root
privileged helper; NetworkManager and D-Bus inside the disposable container.
The browser is deliberately not an actor here; it arrives in the follow-on task.

Primary scenario:
A developer or the gate runs the appliance verification stage -> the stage
builds a network-capable image, creates a disposable network, starts D-Bus,
NetworkManager, the root helper, and an unprivileged appliance-profile Bench
Core with generated TLS material and a built interface directory -> the stage
reports the core listening over HTTPS, `/api/v1/network/status` answers with
adapters NetworkManager actually detected in that namespace, and the
developer's own interface list and default route are unchanged.

Examples:
`cmd/nilo/network_system_linux_test.go::TestApplianceSystemHTTPSAndHelperRecovery`
already starts exactly this pairing - real helper, real NetworkManager,
`--profile appliance --bind 127.0.0.1:0`, TLS minted in memory by
`httptest.NewTLSServer`, a one-file `--gui-dir` - but only as root inside
`02_Tools/tests/network/`, behind `NILO_NETWORK_SYSTEM=1`, and outside
`aegis_test.py full`. `02_Tools/tests/network/run.sh` already starts
`dbus-daemon` and `NetworkManager`, waits for `nmcli general status`, brings up
a real `eth0` with fixed v4/v6 addressing, and then runs the helper and
appliance suites.

Counterexamples:
A stage that reaches an appliance-profile backend by putting a fake driver,
fake provider, or recorded fixture behind the helper socket. That is the
simulation this programme of work exists to remove, relocated one layer down,
and it is explicitly not what this task builds.

In scope:
- A network-capable verification container image carrying the pinned
  toolchain, a browser engine, `network-manager`, `dbus` and `nftables`,
  pinned by base-image digest and an explicit package list (RULING-003).
- A reusable fixture that starts D-Bus, NetworkManager, the real
  `nilo-nethelper`, and an appliance-profile Bench Core with generated TLS
  material and a built interface directory.
- A gate stage that runs the fixture, and the routing needed to reach it from
  the documented verification entry points.
- One automated proof that the stage starts the pairing and reads adapters
  NetworkManager actually detected.
- Reconciling `.agentic/knowledge/repository-toolchain.md`, a legacy page with
  no `## Routing` section, for the files this task touches.

Out of scope:
- Moving the browser suite onto the stage.
- Moving the Go unit suites off the in-memory simulation provider.
- Removing anything: the simulation profile, the GUI contract mock,
  `02_Tools/scripts/nilo-dev.ps1`, or the sigrok `--simulation` flag.
- Document and requirement reconciliation beyond the toolchain knowledge page.
- Changing the locked build image's security posture, its lock, SBOM,
  provenance, or archive.
- Offline reproducibility apparatus for the new image - lock file, SBOM,
  provenance, multipart LFS archive, acceptance evidence (RULING-003).

Constraints:
- The locked build container runs `--network none --cap-drop all
  --security-opt no-new-privileges`, and `verify-host-isolation.sh` proves that
  from the host side. The existing network harness needs `--cap-add NET_ADMIN
  --cap-add SYS_ADMIN` and its own engine network. One run cannot be both.
- `02_Tools/tests/build-environment/verify-offline.sh` executes inside the build
  container, which is given no engine socket by design, so it cannot start a
  sibling container. A stage that needs its own network must be driven from the
  host side of that boundary.
- `newApplianceProvider` is Linux-only, refuses to run as root, requires an
  absolute socket path, and calls `Reconcile` and `Interfaces` across the socket
  before startup continues. Nothing starts without a helper answering.
- The appliance profile requires `--tls-cert`, `--tls-key` and `--gui-dir`, and
  forces HTTPS session cookies.
- REQ-TEST-baa6a1bf requires the network tests to leave the developer host's
  interfaces and default route unchanged.
- `02_Tools/containers/build/` is the in-flight candidate of TASK-998d1b00
  (stage `build`, blocked). Its committed state is in this branch's ancestry;
  its remaining work is not.
- Repository Git authority: the human commits. This task stages nothing,
  commits nothing, and pushes nothing.

- `/api/v1/network/status` answers with adapters NetworkManager detected in the

## Design

**Requirements coverage.**
- REQ-PLAT-32b81548 - one image definition, extended in place rather than
  forked: `02_Tools/tests/network/Dockerfile` gains Node.js and the pinned
  browser engine beside the NetworkManager, D-Bus and nftables it already
  carries, and an `inventory.json` records what a probe must find.
- REQ-TEST-3a6e2094 - `02_Tools/tests/appliance/run.sh` starts the pairing
  inside the container; `cmd/nilo/appliance_stage_linux_test.go` proves it.
- REQ-TEST-4138ae32 - the same Go test cross-checks Bench Core's adapter list
  against `nmcli` in the same namespace.
- REQ-TEST-6072fc2d - `02_Tools/tests/appliance/check.sh` records the host's
  interface list and default route before and after, creates and removes its
  own engine network, and fails on any difference.
- REQ-TEST-a276c88a - the same `check.sh` performs its prerequisite checks
  before doing any work; `test_appliance_stage.py` drives each refusal.

**Component responsibilities.** *Repository-local toolchain* owns the image,
the stage entry point and the gate routing. *Bench Core foundation* owns
`02_Tools/tests/network/` and `internal/nethelper/` per its Routing, and owns
the Go stage proof beside its existing system test. The stage reuses Bench
Core's existing NetworkManager bring-up rather than restating it.

**Interfaces and contracts.**
- `02_Tools/tests/appliance/check.sh [test-selector...]` - host entry point.
  Exit 0 stage passed, 2 prerequisite refusal (named), 1 stage failure.
  Honours `NILO_APPLIANCE_DISTRO` the way `tests/network/check.sh` honours
  `NILO_NETWORK_DISTRO`.
- `02_Tools/tests/appliance/run.sh` - in-container, refuses unless
  `/.dockerenv` exists and `NILO_APPLIANCE_STAGE=1`, mirroring `run.sh`'s
  existing opt-in guard.
- `02_Tools/tests/network/network-up.sh` - new shared bring-up: `dbus-daemon`,
  `NetworkManager`, wait for `nmcli general status`, configure `eth0` with the
  fixed v4/v6 addressing, wait for DAD. Sourced by both `run.sh` and the
  appliance stage, so one apt list and one bring-up stay in one place.
- The Go proof is gated by `NILO_APPLIANCE_STAGE=1` so a developer's
  `go test ./...` skips it, matching `NILO_NETWORK_SYSTEM`'s precedent.

**Data ownership and state transitions.** The stage owns one temporary root
under `/tmp` inside the container holding `state/` (helper), `data/` (core),
`tls/` and `gui/`. TLS material is minted in-process by `httptest.NewTLSServer`
and written to that root, as `network_system_linux_test.go` already does; no
certificate is checked in and none outlives the container. The container is
`--rm`; the engine network is removed by the entry point's trap.

**Execution flow.** `check.sh` records host state -> verifies prerequisites ->
builds the image -> creates a disposable engine network -> `docker run --rm`
with `NET_ADMIN`, `SYS_ADMIN` and that network -> `run.sh` sources
`network-up.sh`, builds `nilo`, `nilo-nethelper` and the stage test from the
read-only mount, starts the root helper, and runs the stage test as an
unprivileged UID -> the test starts Bench Core on `--profile appliance
--bind 127.0.0.1:0` with TLS and a `--gui-dir`, reads the listening record from
stdout, and asserts -> `check.sh` removes the network and re-reads host state.

**Failure recovery.** Every wait is bounded, following `run.sh`'s existing
attempt-counter idiom. The entry point's `trap` removes the container and the
network on any exit path, and the final host comparison runs even after a
stage failure so a run that changed the host is reported as such rather than
masked by the earlier error.

**Security and trust boundaries.** The stage is the one place in the gate that
runs with `NET_ADMIN`/`SYS_ADMIN`; that is why it is a separate image and a
separate entry point from the locked build container, which keeps
`--network none --cap-drop all`. Nothing in this task touches the locked
container, its lock, SBOM, provenance or archive. The helper runs as root and
Bench Core as an unprivileged UID inside the container, exactly as the
appliance ships and as `newApplianceProvider` requires.

**Compatibility and migration.** Nothing is removed. `--profile simulation`,
the browser suite, `nilo-dev.ps1` and the GUI mock are untouched, so both
existing gate routes stay green. Extracting the bring-up out of `run.sh` must
leave `tests/network/check.sh` behaving identically; that is proven by running
it, because its tests are not in the repository gate.

**Observability.** `check.sh` prints the prerequisite it refuses on, the
network it created, and the host interface/route comparison. `run.sh` prints
`nmcli device show` before the proof, as it already does, so a failure is
diagnosable from the log alone.

**Test seams.**
- REQ-PLAT-32b81548 - `test_appliance_stage.py` asserts the Dockerfile's base
  is a digest and its package list explicit; `inventory.json` drives the
  in-image probe.
- REQ-TEST-3a6e2094, REQ-TEST-4138ae32 - `appliance_stage_linux_test.go`.
- REQ-TEST-6072fc2d - `check.sh`'s own before/after comparison, plus a source
  assertion in `test_appliance_stage.py`.
- REQ-TEST-a276c88a - `test_appliance_stage.py` drives `check.sh` through Git
  Bash `sh`, which is present on the supported Windows host.

**Alternatives and tradeoffs.**
- *A second, standalone image* was rejected: it would duplicate the apt list
  and the NetworkManager bring-up, two things that must not drift apart.
- *Reusing `TestApplianceSystemHTTPSAndHelperRecovery` unchanged* was rejected:
  it proves the pairing but not the adapter cross-check or host isolation, and
  it is reachable only from the opt-in helper system run.
- *Taking Node and the browser from the repository runtime* is not possible:
  `02_Tools/runtime/linux-x86_64/` carries only Go, uv and Python. Go still
  comes from that mount through `with-go.sh`; Node and the browser are baked
  into the image, Node verified against `NODE_LINUX_AMD64_SHA256` and the
  browser installed at `PLAYWRIGHT_VERSION`, both from `toolchain.versions`.

**Open decisions.** None. The browser engine is in the image by RULING-005,
