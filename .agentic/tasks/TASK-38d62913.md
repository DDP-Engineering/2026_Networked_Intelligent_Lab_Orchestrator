## Frame

Problem: everything first boot needs now works, and none of it is visible. The
browser interface assumes a commissioned appliance: it offers an allowlist
editor whose every change the appliance refuses while provisioning, and says
nothing about the exposure first boot represents.

Desired outcome: an installer opening the appliance during first boot is told
plainly that every eligible adapter is a temporary way in, sees what is
currently carrying management access, and can end that state by choosing the
adapters that keep it.

Actors: the installer or administrator in the browser; Bench Core, which reports
whether the appliance is provisioning and refuses an unsafe choice.

Primary scenario: the browser reads management access -> the appliance reports
it is provisioning -> the interface shows the commissioning workflow in place of
the allowlist editor -> the administrator keeps some adapters and completes,
and the appliance stops following the hardware.

Examples: a Mini PC reached at `https://ddp-remote.local:8443` during first boot
lists built-in Ethernet and Wi-Fi as temporary paths and is commissioned onto
Ethernet alone.

Counterexamples: a container interface is listed but cannot be chosen; an empty
choice is refused before anything is sent; giving up the adapter the browser
arrived on takes a second, explicit action; a viewer is offered no control.

In scope: the provisioning flag on the management-access payload and its
parser, the first-boot panel and its routing, the client call, the mock route,
three-language copy, and component tests.

Out of scope: the ordinary allowlist editor, which is deliberately suppressed
while provisioning rather than altered; device-network assignment, which is the
existing workflow once commissioning frees an adapter.

Constraints: the browser's payload parser is strict, so the new field must be
tolerated as absent and default to commissioned, which is also the safe
direction - an appliance that does not report it gets the ordinary editor, never
an offer to commission. Copy exists in English, German and Romanian or the
message-parity test fails.

Success signals: the panel states the temporary exposure, lists adapters with
their identities and addresses, marks the current path, explains the local-name
scope, refuses an empty choice, confirms before giving up the current path, and
shows no secret.

Evidence:
- OBSERVED `src/api/management-access.ts` - `parseManagementAccess` validates
  every field and rejects the payload on a mismatch, so a new field has to
  default rather than be required.
- OBSERVED `src/components/network/ManagementAccessPanel.tsx:331` - the existing
  panel renders `entry.kind` raw rather than through a translation key; this
  panel matches that rather than inventing `network.kind.*` keys.
- OBSERVED `src/components/shell/AppShell.tsx:396-404` - every management
  callback is withheld under the simulation profile; the new one follows.
- OBSERVED `internal/network/management_access.go` - `ManagementAccessStatus`
  had no way to say the appliance was provisioning, so the browser could not
  know.
- STATED (user, issue #6, GUI requirements) - list eligible interfaces with name,
  stable adapter identity, type, addresses, link state and proposed role;
  explain that .local discovery works only on the local network; identify the
  interface used by the current browser session; prevent assigning it away until
  a replacement is confirmed; explain why ineligible interfaces cannot be
  selected; show usable URLs without displaying secrets.

Assumptions: none beyond the payload contract above.

Unknowns: none blocking.

Decision-blocking questions: none.

Proposed behaviors:
1. The first-boot workflow presents the temporary exposure, the eligible
   adapters and their identities, the current browser path, the usable URLs and
   their scope, and why an ineligible interface cannot be chosen - with no
   secret anywhere.
2. The workflow completes commissioning onto the chosen adapters, refusing an
   empty choice, confirming before giving up the current path, reporting a
   refusal without losing the selection, and offering nothing to an identity
   that may not manage.

Path and reason: full. A new browser surface, a new payload field and a new
client call.

## Design

**Requirements coverage.** REQ-UX-f9c2846a is the panel's presentation;
REQ-UX-5a75d710 its completion workflow. Both need the appliance to say whether
it is provisioning, which is the one backend change.

**Component responsibilities.** *Browser GUI foundation* for the panel, its
routing and the client call; *Bench Core foundation* for the one payload field.
`ManagementAccessStatus.Provisioning` is read from the service's own
provisioning mode, so the browser learns it from the same place the allowlist
derivation does rather than inferring it.

**Interfaces and contracts.** The payload gains `provisioning` (boolean); the
browser parser reads it as `body.provisioning === true`, so an appliance that
omits it is treated as commissioned - the safe direction, because it shows the
ordinary editor rather than offering to commission something already
commissioned. `BenchCoreClient.completeCommissioning(credential, interfaces,
confirmCurrentInterface)` posts to the commissioning route and parses the
ordinary management-access payload back, so the interface shows the result the
transition produced.

**Execution flow.** `NetworkPage` renders `CommissioningPanel` when the status
says provisioning and the callback is present, and suppresses the allowlist
editor in exactly that case. The two are mutually exclusive on purpose: while
provisioning, every change the editor could make is refused by the appliance, so
showing it disabled would offer a control that cannot work.

**Failure recovery.** An empty selection is refused in the browser before
anything is sent. A refusal from the appliance is displayed and the selection is
kept, so the administrator corrects rather than restarts. Giving up the adapter
the session arrived on raises a second, explicit button naming that adapter.

**Security.** The panel renders only fields the payload already carries, none of
which can hold a secret, and a test asserts the rendered text contains no
secret-shaped word. The completion control is withheld from an identity without
the manage permission, and the route enforces that server-side regardless.

**Test seams.** `CommissioningPanel.test.tsx` over a status carrying two
eligible adapters and one container interface: presentation, the current-path
marker, the ineligible explanation, the empty refusal, the confirmation flow,
the ordinary completion, a refusal from the appliance, the viewer case and the
secret sweep. `messages.test.ts` keeps the three languages in parity.

**Alternatives rejected.** Disabling the allowlist editor during first boot -
it would present a control the appliance refuses. Requiring `provisioning` in
the parser - an older appliance would fail the whole parse rather than degrade
to the ordinary editor. Adding `network.kind.*` translation keys - the existing
panel renders the kind raw, and these are not words that translate.

**Expected files.** `internal/network/management_access.go`,
`internal/httpapi/management_access.go`,
`nilo_gui/src/api/management-access.ts`, `client.ts`, `mock.ts`,
`components/network/CommissioningPanel.tsx` (new), `CommissioningPanel.test.tsx`
(new), `components/pages/NetworkPage.tsx`, `components/shell/AppShell.tsx`,
`i18n/{en,de,ro}.ts`, plus the fixtures TypeScript required in
`App.test.tsx`, `AuthenticationPage.test.tsx`, `shell.test.tsx`,
`ManagementAccessPanel.test.tsx` and `NetworkPage.test.tsx`.

**Open decisions.** None.
